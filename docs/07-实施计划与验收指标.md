# 07 实施计划与验收指标

> 所属：卫华产品质量智能平台（Demo）设计文档 ｜ 版本 v0.1 ｜ 2026-11-10
> 本文回答：先做什么、两天怎么排、怎么验收、试点怎么落、有哪些坑。

---

## 一、范围分级

| 级别 | 范围 | 说明 |
|---|---|---|
| **P0（Demo 必做）** | 工作台、报修单列表、问题详情/质量链、问题库问答、协议问答/不符合核对/原文查看、预警中心/预警配置、演示数据与重置 | 8 分钟演示能完整走通 |
| **P1（Demo 可选 / 试点必做）** | 相似问题独立检索、协议浏览、引用核对记录、分析报告、数据源接入、字典配置 | 有余力再加 |
| **P2（规划）** | 权限与审计、OA 回写、移动端、语音提问、复杂归因下钻 | 试点后按需 |

**P0 的取舍原则**：宁可少三个页面，也要保证三个「高潮页」（M1-03、M2-01、M3-03）体验完整、数据自洽、引用可跳。

## 二、两天 Demo 排期

假设 2 名开发（1 前端 + 1 后端/AI）+ 1 名产品兼演示，工作量为 2 个工作日。

| 时间 | 前端 | 后端 / AI | 产品 |
|---|---|---|---|
| D1 上午 | 框架、导航、工作台骨架 | 数据模型建表、演示数据导入 | 数据核对、页面文案 |
| D1 下午 | M1-02、M1-03 静态版 | 要素抽取、四轴召回、质量链接口 | 走查研判流程 |
| D2 上午 | M2-01 答案卡、M2-04 原文高亮 | 协议检索、答案组装、引用接口 | 核对 5 条标准答案 |
| D2 下午 | M2-02、M3-03、M3-04 | 预警规则计算、配置保存、缓存 | 彩排 + 兜底检查 |

**关键路径**：演示数据 → 检索 → 答案 → 引用跳转。数据不自洽，后面全塌。

### 2.1 建议的搭建顺序

1. 先定 JSON 数据包（不写代码也能先把 100 条报修单、3 份技术协议、页码准备好）。
2. 再做「数据 → 接口 → 页面」的贯通（先丑后美）。
3. M2 的引用跳转优先于其他交互（这是信任的基础）。
4. 最后做驾驶舱图表（视觉收益高，但对演示逻辑不关键）。

## 三、技术选型与依赖

| 层 | 选型 | 理由 | 风险 |
|---|---|---|---|
| 前端 | React + Vite + TypeScript | 与售后项目一致，复用组件与样式习惯 | 无 |
| 后端 | FastAPI + SQLAlchemy + SQLite | 与售后项目一致，两天可交付 | SQLite 并发弱，Demo 够用 |
| 全文检索 | SQLite FTS5 | 零依赖，中文分词用 jieba 预处理 | 词典需手工维护 |
| 向量 | 本地 `bge-small-zh-v1.5`（sentence-transformers）或 numpy 预计算 | 离线可跑，不依赖网络 | 首次加载慢，需预热 |
| 大模型 | DeepSeek `deepseek-chat`（OpenAI 兼容） | 与售后项目一致，中文好，成本低 | 网络/限流；需缓存兜底 |
| 文档解析 | PyMuPDF（PDF）、python-docx（DOCX） | 能拿页码与坐标 | 扫描件不行，Demo 用预解析包绕过 |
| 图表 | Recharts 或 ECharts | 轻量、够用 | 无 |
| 部署 | 本机 `uvicorn` + `vite preview`，单机演示 | 简单 | 现场网络 |

### 3.1 外部依赖清单

- [ ] DeepSeek API Key（或兼容网关）
- [ ] 演示机（16G 内存以上，能本地跑 embedding 模型）
- [ ] 预解析协议包（3 份 PDF，共 624 块；其中 2001001111 另有 12 条结构化条款）
- [ ] 100 条报修单、11 台整机、5 条预警规则（4 条命中）、5 条问答缓存的演示数据
- [ ] 大屏/投屏与备用热点

## 四、里程碑

| 阶段 | 时间 | 交付 | 出口条件 |
|---|---|---|---|
| **M0 设计** | 本周 | 本套文档 | 评审通过，范围与口径确认 |
| **M1 Demo** | 2 天 | 可演示系统 + 演示数据包 | 8 分钟脚本无卡点，5 条问答全对 |
| **M2 试点准备** | 2 周 | 真实数据接入（只读）、评测集、试点方案 | 3 个数据源接通，评测基线测出 |
| **M3 试点** | 4～6 周 | 1 个售后组 + 1 个检验组使用 | 指标较基线改善，用户愿意继续用 |
| **M4 推广** | 3 个月 | 全公司 + 回写 OA/整改 | 覆盖率、闭环率达标 |

### 4.1 试点前置条件

1. 产品编号在 SAP / 售后 / 追溯三套系统里一致（或给出映射规则）。
2. 至少 50 台整机的合同、技术协议、图纸电子版可获取。
3. 近 2 年质量问题数据可导出（含处理方法和原因归属）。
4. 部件与原因字典的负责人确定（质量部）。
5. 明确「AI 结论不作为责任认定依据」的制度口径。
6. 指定 2 名业务专家做评测标注（每周 2 小时）。

## 五、验收清单

### 5.1 功能验收（Demo）

| # | 验收项 | 通过标准 |
|---|---|---|
| 1 | 整机上下文 | 选一台整机后，M1/M2/M3 均围绕该整机 |
| 2 | 报修单列表 | 100 条、筛选/分页可用、点击进详情 |
| 3 | 问题研判 | 打开报修单，60 秒内出相似历史、质量链、建议 |
| 4 | 相似召回 | 演示集 5 条应召回问题全部出现在前 5 |
| 5 | 命中原因 | 每条历史问题显示「同客户/同机型/同部件/相似度」 |
| 6 | 质量链 | 7 段可见，断点明确标注 |
| 7 | 问题库问答 | 能汇总 100 条问题；DeepSeek 未配置时回退规则摘要 |
| 8 | 协议问答 | 能搜索并选中 3 份协议；Q1～Q5 答案与标准答案一致，Q6/Q7 正确拒答或部分回答 |
| 9 | 引用 | 每条结论有引用；点击定位到正确页码并高亮 |
| 10 | 数字校验 | 模型结论中的数字均可回溯到条款原文 |
| 11 | 不符合核对 | 140μm 判「不符合协议要求」，160μm 判「符合」（箱梁内部 ≥150μm） |
| 12 | 统计报表 | 问题库问答输入「缓冲器和制动器」，Excel/PDF/Word 均可下载；缓冲器 12 条、制动器 5 条分别成表，含柱状图/饼图，不含 Top 10 和问题明细 |
| 12 | 预警配置 | 5 条规则可改，保存即时重算；阈值 2→1 多一条预警 |
| 13 | 预警中心 | 卡片显示条件、阈值、窗口、证据、涉及整机/客户 |
| 14 | 处置 | 预警可确认/转整改/误报，状态变化可见 |
| 15 | 驾驶舱 | 4 个 KPI、趋势、原因分布、高频部件有真实数据 |

### 5.2 体验验收

- 任意页面 2 次点击内能回到整机上下文。
- 所有 AI 内容有标识，所有数字有出处。
- 加载有分步提示，超过 8 秒有可读内容。
- 空态、错误态都有下一步动作。
- 演示全程无需鼠标精确操作（大按钮、可键盘）。

### 5.3 数据验收

- 100 条报修单、11 台整机、3 份技术协议（624 块原文）、5 条预警规则（4 条命中）全部可用。
- 交叉引用一致：报修单里提到的整机/部件/文档在库中存在。
- 演示数据全部打「演示数据」标。
- DeepSeek 已配置时，两个问答入口返回真实模型结果并显示模型名/耗时；未配置时回退规则模式并提示。

## 六、指标口径与基线

### 6.1 效率指标

| 指标 | 公式 | 数据来源 | 基线测法 |
|---|---|---|---|
| 单条问题研判耗时 | 从提交问题到看到研判结果 | 系统日志 | 现有流程：找 3 个人各测 5 条，计时 |
| 单次档案核对耗时 | 从提问到拿到可用结论 | 系统日志 + 人工记录 | 跟随检验员 5 次，计时 |
| 单次不符合核对耗时 | 从发现不符合到判定完成 | 人工记录 | 同上 |

### 6.2 质量指标

| 指标 | 公式 | 说明 |
|---|---|---|
| 相似问题召回率 | 召回的正确历史问题数 / 应召回总数 | 人工标注 50 对 |
| 引用准确率 | 引用支撑结论的条数 / 总引用条数 | 抽检 50 条，目标 100% |
| 答案正确率 | 与人工标准答案一致的条数 / 总条数 | 评测集 20 条 |
| 预警准确率 | 人工确认为真的预警数 / 总预警数 | 试点首月全量复核 |
| 预警提前量 | 问题首次聚集到预警发出 | 对比原月度复盘时间 |
| 复发率 | 12 个月内同部件同现象重复问题数 / 问题总数 | 季度统计 |
| 平均闭环时长 | 平均（关闭时间 − 发现时间） | 月度 |
| 质量链完整度 | 7 段齐全的问题占比 | 月度，反映追溯水平 |

### 6.3 价值测算（试点后填）

```
月节省工时 = （人工单次耗时 − 系统单次耗时）× 月处理量
月节省成本 = 月节省工时 × 工时单价
年化收益 = 月节省成本 × 12 + 复发率下降带来的售后成本节约
投入 = 开发 + 模型调用 + 运维
ROI = 年化收益 / 投入
```

> 基线必须在试点前测，和售后项目（`weihua_shouhou`）的做法一致：先测现状，再用同一口径复测。

## 七、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 协议电子版缺失/版本混乱 | M2 无法回答，信任崩塌 | 试点先锁定协议最新版本；缺文件时明确显示「未入库」 |
| 部件/原因字典不统一 | 检索和统计都不准 | 先做 200 个高频部件的归一词典，配人工兜底 |
| 大模型答错或编造 | 用户不再信任 | 引用 grounding + 数字校验 + 拒答话术 + 人工确认 |
| 演示现场网络不稳 | 演示失败 | 缓存模式 + 本地模型兜底 + 录屏备份 |
| 数据敏感（客户、金额、人员） | 合规风险 | 密级、脱敏、权限矩阵、导出水印 |
| 预警被当成考核工具 | 员工抵触、数据造假 | 制度上明确「改进用途」，列表脱敏，可申诉 |
| 与现有系统集成排期长 | 试点延期 | 只读优先、文件导入兜底、接口适配器解耦 |
| 模型成本超预期 | 预算压力 | 缓存、批处理、小模型分流、限制上下文长度 |
| 业务方不参与 | 做出来没人用 | 每周 2 小时专家标注 + 试点用户深度参与设计 |

## 十、下一步（本设计通过后）

1. 评审本套文档，锁定 P0 范围与「待确认清单」中的 1～4 项。
2. 产出演示数据包（JSON + 页面截图），先不写业务代码。
3. 搭页面骨架，用假数据走通三条主线。
4. 接真实模型，跑 20 条评测集，修 badcase。
5. 彩排 3 次，形成兜底录屏。
6. 试点立项：定数据源、定评测集、定成功标准。
