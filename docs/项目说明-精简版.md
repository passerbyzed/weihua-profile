# 产品质量智能平台 · 项目说明（精简版）

> 版本：2026-11 ｜ 形态：PC Web + 飞书 H5 ｜ 当前为 Demo，数据为构造数据

## 一、解决什么问题

售后、质量、技术、报价查同一台设备的信息，要跨 OA、售后系统、档案目录、个人电脑反复找：

- 一个售后问题来了，历史是否出过、当时怎么处理、根因是什么，靠人回忆和翻记录；
- 技术协议几十页，问一个油漆/吊钩/钢板要求，要逐页翻，还容易看漏版本；
- 同类问题反复出现，靠月度汇总才发现，发现时已经出了多起；
- 每次汇报要手工拉数据、做 Excel，统计口径还不一致。

平台把「问题、整机、协议、规则」放到一个可追溯的工作台，让上述动作变成一次检索、一次问答、一条预警、一键报表。

## 二、方案

### 2.1 三个模块

| 模块 | 做什么 | 当前 Demo 覆盖 |
|---|---|---|
| M1 售后问题质量库 | 报修单检索；相似历史召回；7 段质量链；根因假设与处置建议；问题库问答；统计报表 | 100 条报修单、11 台整机、10 家客户；主样例召回 6 条相似（5 条高相似）、质量链 6/7 |
| M2 技术协议库 | 搜索并选中 PDF 协议；按问题返回逐字原文；条款页码引用；不符合项核对 | 3 份协议（55/74/63 页）、624 块原文；问答逐项带页码 |
| M3 质量归因预警 | 按故障类型、原因归属、厂家、部件、备注关键词配规则；时间窗口 + 次数阈值；AI 建议 + 人工备注 | 5 条规则、4 条命中；规则保存后实时重算 |

### 2.2 技术路线

```
OA / 售后 / 档案(PDM) / 供应商
        │  API、文件、增量同步
        ▼
数据层：报修单 · 整机/客户/合同 · 协议原文/条款 · 预警规则
        ▼
能力层：相似召回 · 质量链 · 原文检索 · 规则计算 · 报表生成
        ▼
应用层：问题库 · 技术协议库 · 预警中心 · 工作台
        ▼
PC Web / 飞书 H5
```

- 前端 React + TypeScript；后端 Python；Demo 使用本地 JSON，试点接 OA/数据库。
- 大模型只用于问题归纳、建议生成；技术协议问答**不调用模型**，只返回原文。
- 预警、判定、统计由规则引擎计算，结果可复现、可审计。

### 2.3 可信机制

- 每条协议回答带「文件 + 页码」，引用可点开核对；
- 每个预警带规则条件和证据问题，人工确认后才流转；
- 每个数字来自原始工单或协议原文，不由模型编造。

## 四、后续怎么落地

### 4.1 需要 OA 提供的接口

| 接口 | 关键字段 | 用途 | 优先级 |
|---|---|---|---|
| 售后报修单列表/详情/增量 | 报修单号、质量问题号、整机号、客户、部件、现象、描述、故障类型、原因、售后状态、定责状态、报修时间、更新时间、附件 | M1 主数据 | P0 |
| 整机/客户/合同主数据 | 产品编号、机型、规格、客户、合同号、出厂/交付日期、质保期 | 问题上下文、质量链 | P0 |
| 技术协议/图纸/ECN | 文件 ID、类型、版本、生效日期、页数、下载/预览地址、关联整机/合同 | M2 原文与引用 | P0 |
| 组织/用户/SSO | 用户 ID、姓名、部门、角色、租户 | 登录、权限、数据范围 | P0 |
| 附件/文件服务 | 文件上传、下载、预览、签名 URL | 问题附件、协议原文 | P0 |
| 供应商/厂家 | 供应商 ID、名称、类别 | 预警规则、责任归属 | P1 |
| 待办/消息 | 待办创建、消息卡片、状态回调 | 预警推送、整改闭环 | P1 |
| 字典 | 故障类型、原因归属、售后状态、来源、部门 | 口径统一 | P1 |

**接口要求**：HTTPS + OAuth2/客户端凭证；支持 `updated_at` 增量、分页、幂等 ID；提供测试环境与字段字典；文件走签名 URL，不直传二进制；限流和失败重试可配置。

### 4.2 部署飞书 H5

1. 飞书管理后台创建**企业自建应用**，启用 H5，配置应用主页、重定向 URL、可信域名。
2. H5 使用飞书免登：前端取 `requestAuthCode`，后端换取用户身份，与 OA 用户 ID 映射。
3. 前端静态资源与 `/api` 同域部署在 HTTPS 域名下，反向代理到后端；配置飞书可信域名和 IP 白名单。
4. 移动端适配：问题列表/详情、协议问答、预警卡片优先；预警用飞书消息卡片推送到责任人，点开进入 H5 详情。
5. 权限：按 OA 部门/角色 + 客户/产品数据范围授权；协议原文和附件走签名 URL，记录访问日志。

### 4.3 实施节奏

| 阶段 | 周期 | 交付 |
|---|---|---|
| P0 接口联调 | 2 周 | 报修单、整机/合同、协议文件、SSO 四个 P0 接口；3～6 个月历史数据回填 |
| P1 PC 试点 | 2～3 周 | 1 个产品线、1 个质量/售后小组；问题研判、协议问答、预警、报表跑通 |
| P2 飞书 H5 | 2 周 | 自建应用、免登、移动端、预警消息卡片；10～20 人试点 |
| P3 推广 | 1～2 月 | 扩产品线/客户；按真实工单校准规则和收益；形成接口与权限规范 |

### 4.4 试点验收指标

- 单条问题研判 ≤5 分钟；
- 技术协议查询 ≤1 分钟，引用页码准确率 100%（抽检 50 条）；
- 统计报表 ≤1 分钟/份，Excel/PDF/Word 均可下载；
- 预警每日计算，规则保存后立即生效；
- 报修单增量同步延迟 ≤5 分钟，历史数据完整率 ≥99%。

## 五、边界

- 不自动判定质量责任、不自动派工；AI 只给建议，人工确认后生效。
- 试点前需完成 OA 接口和权限梳理；数据质量不足时，先补主数据和历史工单，再谈模型效果。
