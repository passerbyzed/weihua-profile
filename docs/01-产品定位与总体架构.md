# 01 产品定位与总体架构

> 所属：卫华产品质量智能平台（Demo）设计文档 ｜ 版本 v0.1 ｜ 2026-11-10

---

## 一、问题与现状

### 1.1 三个具体痛点

**痛点 A：售后问题靠人回忆和翻旧单据**

| 项 | 现状 |
|---|---|
| 谁在做 | 售后工程师、质量工程师 |
| 怎么做 | 接到新报修后，凭记忆判断「这个问题以前是不是出过」；需要时翻 OA 报修记录、翻微信、问老同事 |
| 痛点 | 同名部件在不同单据里叫法不同（吊钩 / 钩头 / 吊钩组），检索基本靠关键词碰运气；同一个客户、同一型号的历史问题散落在不同系统 |
| 后果 | 重复问题重复排查、重复付成本；同类问题反复发生却没人发现规律；新人上手要 1～2 年 |

**痛点 B：检验发现不符合，要跨三个地方核对**

| 项 | 现状 |
|---|---|
| 谁在做 | 检验员、技术/设计工程师 |
| 怎么做 | 实测值与要求不符时：先翻图纸看有没有标注 → 再翻技术协议看有没有非标约定 → 再确认申报/报价时按什么标准报的 → 三方不一致就挨个打电话 |
| 痛点 | 合同、技术协议、图纸、变更单分散在文件服务器、PDM、个人电脑；同一项要求在不同文档里版本不同；问一个人要等半天 |
| 后果 | 单次核对 20～40 分钟；判定口径不一致；「图纸没标但协议要求了」这种漏项到售后才暴露 |

**痛点 C：质量分析靠月度人工统计，发现太晚**

| 项 | 现状 |
|---|---|
| 谁在做 | 质量部 |
| 怎么做 | 每月从质量优化、质量问题反馈、售后服务、质量追溯各系统导表，人工合并、分类、做图 |
| 痛点 | 口径不统一、合并靠 Excel；班组和设计人员维度的问题分布算不出来；异常要等下个月 |
| 后果 | 某班组同类问题三个月出了五起，季度复盘才发现；改进措施无法验证是否有效 |

### 1.2 数据现状

| 系统 | 里面有什么 | 谁在用 | 主要问题 |
|---|---|---|---|
| 售后服务平台（`weihua_shouhou`） | 报修单、产品编号、故障类型、原因归属、问题部件、问题描述、处理方法、通话转写 | 售后 | 字段是自由文本，部件名不统一；无历史关联 |
| 质量问题反馈 | 客户反馈函、投诉、处理结果 | 质量部、销售 | 多为 Word/PDF 附件，未结构化 |
| 质量优化 | 整改单、措施、验证、费用 | 质量部 | 与具体整机/部件关联弱 |
| 质量追溯平台 | 班组、工序、炉批号、铭牌、检验记录 | 质检、生产 | 只在追溯时用，不做分析 |
| OA | 报修单、审批、任务 | 全员 | 流程数据，不承载技术细节 |
| SAP | 合同、物料、BOM、供应商 | 计划、采购 | 主数据权威，但业务人员不好查 |
| 图纸 / PDM、文件服务器 | 合同、技术协议、图纸、变更单 | 技术、检验、报价 | 非结构化，检索靠人 |

### 1.3 共性根因

1. **没有统一主键**：数据按系统割裂，缺一个「整机」主键把合同 → 图纸 → 检验 → 售后串起来。
2. **档案不可检索**：合同、协议、图纸是非结构化文档，只能靠人翻、靠人问。
3. **经验不沉淀**：老售后的判断在脑子里，没有形成可检索的「问题—原因—措施」三元组。
4. **分析太滞后**：统计靠月度人工，异常发现晚于问题扩散。

这四条正好对应本系统的四层设计：**一机一档 → 技术协议库 → 问题质量库 → 归因预警**。

## 二、目标用户与典型任务

| 角色 | 典型任务 | 现在耗时 | 在本系统里做什么 | 成功标志 |
|---|---|---|---|---|
| 售后工程师 | 接到报修，判断是否老问题、怎么处理 | 30～60 分钟（翻查+问人） | M1 问题研判：录入/同步问题 → 看相似历史与建议 | 1 分钟内看到高相似历史与当时措施 |
| 质量工程师 | 问题归因、跟踪整改、月度分析 | 半天～2 天/次 | M1 研判、M3 归因与预警、报告 | 归因有证据链，报告自动生成初稿 |

## 三、产品定位

**一句话**：面向起重机的「整机质量档案 + AI 研判」平台，让每一个质量问题都能追到图纸和协议，让每一份档案都能被问出来。

**三个价值主张**

1. **查得到**：任何一台设备的质量历史，按「客户 / 机型 / 部件 / 现象」四轴一次召回。
2. **说得清**：任何一条 AI 结论都带出处，点开就是原文那一页那一条。
3. **早发现**：班组、设计人员、供应商、机型维度的异常聚集，从月度提前到实时。

**不做什么**

- 不做新的报修系统、不替代 OA 流程、不做 ERP。
- 不对质量责任做自动判定，只给线索和证据，结论由人确认。
- 不追求「全量文档自动解析」，先保证关键档案（合同、技术协议、图纸、变更单）可检索、可引用。

## 四、设计原则

| 原则 | 含义 | 落到设计上的约束 |
|---|---|---|
| **一机一档** | 以整机产品编号为主键，把所有质量信息挂上去 | 所有业务表必须有 `machine_id`；无整机归属的数据进「待归档」池 |
| **证据优先** | AI 结论必须可回溯到原始记录或原文 | 每条结论挂 `evidence[]`；无证据只能显示「未找到依据」，不能给结论 |
| **双通道检索** | 结构化过滤 + 语义相似并用 | 同客户/同机型/同部件走结构化，现象描述走向量+关键词 |
| **人机协同** | AI 出初稿，人做确认 | 引用、预警、归因都有「确认 / 有异议」动作，留痕 |
| **闭环** | 问题 → 归因 → 整改 → 验证 → 关闭 | 状态机完整，关闭必须带验证结果 |
| **渐进落地** | 先 Demo 后试点，先只读后回写 | 数据接入只读优先；回写只写本系统自己的表 |

## 五、总体架构

### 5.1 五层架构

```
┌──────────────────────────────────────────────────────────────────────┐
│ 应用层                                                                │
│  工作台 │ 售后问题质量库 M1 │ 技术协议库 M2 │ 质量归因预警 M3 │ 配置    │
└──────────────────────────────────────────────────────────────────────┘
                                  ▲
┌──────────────────────────────────────────────────────────────────────┐
│ AI 能力层                                                             │
│  要素抽取 │ 混合检索 │ 质量链补全 │ 归因推理 │ 预警规则 │ 报告生成      │
│  （大模型 + 规则 + 统计，全部输出结构化 JSON + 证据 + 置信度）          │
└──────────────────────────────────────────────────────────────────────┘
                                  ▲
┌──────────────────────────────────────────────────────────────────────┐
│ 质量数据底座                                                          │
│  主数据：客户 / 合同 / 整机 / 机型 / 部件 / 班组 / 人员 / 供应商       │
│  事实数据：质量问题 / 检验记录 / 追溯记录 / 售后报修 / 反馈函 / 整改    │
│  档案数据：文档 / 条款 / 图纸标注 / 引用 / 版本                        │
│  字典：部件归一 / 故障现象 / 原因分类 / 标准配置库                      │
└──────────────────────────────────────────────────────────────────────┘
                                  ▲
┌──────────────────────────────────────────────────────────────────────┐
│ 接入与治理层                                                          │
│  适配器（API / DB 视图 / 文件 / 手工导入）│ 清洗归一 │ 幂等去重 │ 质量校验 │
└──────────────────────────────────────────────────────────────────────┘
                                  ▲
┌──────────────────────────────────────────────────────────────────────┐
│ 数据源层                                                              │
│  售后服务平台 │ 质量问题反馈 │ 质量优化 │ 质量追溯 │ OA │ SAP │ 图纸/PDM │
└──────────────────────────────────────────────────────────────────────┘
```

### 5.2 一次数据流转（以售后问题为例）

```
售后服务平台产生报修单
  → 适配器拉取（产品编号、故障类型、部件、描述、处理方法）
  → 清洗：部件名归一（"钩头"→吊钩组）、关联整机、关联合同
  → 落库：QualityIssue（source=售后）
  → AI：要素抽取 → 四轴召回 → 质量链补全 → 生成研判结论（带证据）
  → 界面：M1 问题详情右侧「AI 研判」面板
  → 人工确认/修正 → 结论回写（is_confirmed=true，保留原始 AI 版本）
  → 汇总：进入 M3 归因统计与预警
```

关键点：**AI 结论可重算**。原始数据、抽取结果、AI 结论三层分开存，换模型或换 Prompt 可以重跑，历史结论不被覆盖。

## 七、与现有平台的集成

### 7.1 集成原则

1. **只读优先**：除本系统自有表外，不修改源系统数据。
2. **幂等**：同一单据重复拉取不产生重复记录（源单号唯一约束 + 内容哈希）。
3. **可回溯**：每条记录保存来源系统、来源单号、拉取时间、原始报文摘要。
4. **失败隔离**：源系统不可用时，本系统降级为「上次同步快照」，不阻塞主流程。
5. **口径唯一**：统计口径以本系统字典为准，源系统字典做映射表。

### 7.2 集成清单

| 系统 | 数据 | 方向 | 方式 | Demo 做法 |
|---|---|---|---|---|
| 售后服务平台 | 报修单、转写、产品编号 | 入 | REST 拉取 / DB 只读视图 | 适配器 + 样例 JSON，模拟 10 条报修单 |
| 质量问题反馈 | 反馈函 | 入 | 文件监听 + 手工上传 | 预置 3 份反馈函文本 |
| 质量优化 | 整改单、验证 | 双向 | REST | 只做「整改任务」本地表 |
| 质量追溯 | 班组、工序、炉批、铭牌 | 入 | DB 视图 | 预置追溯记录 12 条 |
| OA | 审批、待办 | 出 | REST | 生成任务卡片，不真发 |
| SAP | 合同、BOM、供应商 | 入 | 接口 / 导出表 | 预置 11 台整机与合同 |
| 图纸 / PDM | 图纸、协议、变更 | 入 | 文件同步 | 预解析档案包（JSON + 页面图） |

## 八、术语表

| 术语 | 定义 | 说明 |
|---|---|---|
| **整机 Machine** | 一台具体设备，以产品编号唯一标识 | 质量数据的唯一主键，如 `LD5-2024-0316` |
| **机型 MachineModel** | 型号规格族，如 `LD5-10.5 A5` | 「同机型」检索按机型编码 + 规格相近 |
| **部件 Component** | 归一后的标准部件，如「起升机构/卷筒/轴承座」 | 通过部件词典把自由文本归一 |
| **质量链** | 从需求到售后的七段证据链 | 缺哪段就标「证据缺失」 |
| **档案 Document** | 合同、技术协议、图纸、变更单、检验标准等 | 带版本、生效日期、密级 |
| **条款 Clause** | 档案中的一条可引用单元 | 有章节号、页码、原文、类型 |
| **引用 Citation** | AI 结论指向某条款的一次引用 | 含原文片段、置信度、核对状态 |
| **归因 Attribution** | 问题原因的判定 | 分责任类型（设计/制作/外协/来料/使用…）与根因分类 |
| **复发 Recurrence** | 同整机或同部件同现象 12 个月内再次发生 | 用于预警和有效性评估 |
| **报修单 Repair Order** | 售后受理后形成的一张服务单，编号 `FN…` | M1 列表的主对象 |
| **质量问题 Quality Issue** | 由报修单/检验/反馈函转成的质量记录，编号 `QI…` | 与报修单 1:1 关联 |
| **售后状态** | 待派工 / 已派工-待完工 / 已完工-待评价 / 已完工-已评价 / 已取消 | 售后视角的状态 |
| **定责状态** | 未开始 / 待定 / 有责 / 无责 | 质量定责视角的状态 |
| **预警规则** | 故障类型 + 原因归属 + 厂家 + 问题部件 + 备注关键词 + 窗口 + 阈值 | 满足条件的问题数达阈值即预警 |
| **非标 Non-standard** | 与标准配置库或企业标准不一致的要求 | 分：非标 / 模糊 / 不满足 / 可偏离 / 未提及 |
| **核对闭环** | 人工确认 AI 引用或结论的动作 | 留痕，供审计与追责 |

## 九、成功标准

### 9.1 定性标准（Demo 验收）

1. 演示三条主线各一次，全程不卡顿、不出现明显错误答案。
2. 每一个 AI 结论都能一键跳到原文/原始单据。
3. 无依据时明确说「未找到」，不编造。
4. 观众能听懂「这台设备出过什么问题、当时怎么处理、依据在哪」。

### 9.2 定量指标（试点用，基线待测）

| 指标 | 口径 | Demo 目标 | 试点目标 |
|---|---|---|---|
| 单条售后问题研判耗时 | 从录入到看到相似历史 | ≤ 60 秒 | 较人工下降 80% |
| 相似问题召回率 | 人工标注的同类问题中被召回比例 | ≥ 80%（演示集） | ≥ 85% |
| 档案问答首次命中率 | 答案包含正确条款的比例 | ≥ 90%（演示集） | ≥ 90% |
| 引用准确率 | 引用片段确实支撑该结论的比例 | 100% | ≥ 98% |
| 单次非标核对耗时 | 从提问到拿到三方依据 | ≤ 10 秒 | 较人工下降 70% |
| 预警提前量 | 问题聚集到预警发出的天数 | 实时 | ≥ 30 天 |
| 预警规则可配置 | 页面可改条件、窗口、阈值并即时生效 | 支持 | 支持 |
| 问题库规模 | 演示环境报修单/质量问题条数 | 100 条 | 按实际接入 |
| 复发率 | 12 个月内同部件同现象重复发生占比 | 可统计 | 下降 20% |

> 所有数字在试点前先测基线，用同一口径复测，不在方案里先承诺。
